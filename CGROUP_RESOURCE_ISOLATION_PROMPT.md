# Промт: per-job cgroup-изоляция Blender

Исправь архитектуру ограничения ресурсов Blender в проекте Render Node.

Сначала полностью прочитай:

- `AGENTS.md`;
- `PYTHON_PROJECT_ARCHITECTURE.md`;
- `IMPLEMENTATION_STATE.md`;
- соседний код Job Manager, scheduler, GPU discovery и Blender runner;
- текущие незакоммиченные изменения — сохрани пользовательские и несвязанные правки.

## Контекст проблемы

Blender 4.1.1 с Cycles/OptiX на RTX A5000 завершился с `code -6`:

- `Malloc returns null`;
- `System is out of GPU and shared host memory`;
- `std::bad_alloc`.

При этом GPU и системная RAM были свободны. Причина — backend устанавливает Blender-процессу:

```python
resource.setrlimit(resource.RLIMIT_AS, ...)
```

через `SandboxRunner._child_limits()`, а `RENDER_NODE_WORKER_MEMORY_GB=16`.

`RLIMIT_AS` ограничивает виртуальное адресное пространство процесса. CUDA/OptiX резервируют и отображают большие виртуальные диапазоны, поэтому это ограничение вызывает ложный OOM. Это не означает несовместимость RTX A5000 с OptiX.

## Цель

Заменить `RLIMIT_AS` на корректную per-job изоляцию фактически используемой системной памяти через Linux cgroups. Решение должно работать с одной или несколькими GPU разных моделей и не зависеть от заранее известного количества карт.

## Требования

1. Удали применение `RLIMIT_AS` ко всем Blender-процессам. Не заменяй его просто увеличенным глобальным значением.

2. Каждый Blender job запускай:

   - в отдельной process group;
   - в отдельном cgroup;
   - вместе со всеми дочерними процессами Blender.

3. Для cgroup ограничивай:

   - фактическую системную память;
   - swap, если контроллер это поддерживает;
   - число процессов;
   - групповое завершение при OOM, где это поддерживается.

4. Предпочтительный backend — cgroup v2:

   - `memory.max`;
   - `memory.swap.max`;
   - `pids.max`;
   - `memory.oom.group`;
   - `memory.events` для диагностики OOM.

5. Учти текущее окружение, где может использоваться cgroup v1. Реализуй обнаружение версии cgroup без предположений:

   - если доступен делегированный writable cgroup v2 — используй его;
   - если требуется поддержка writable cgroup v1, реализуй минимальный эквивалент либо явно зафиксируй проверенный fallback;
   - не пытайся молча писать в read-only `/sys/fs/cgroup`.

6. Предусмотри два явных режима:

   - `strict/production`: если per-job cgroup создать невозможно, рендер не запускается и возвращается понятная диагностическая ошибка;
   - `trusted/local`: `RLIMIT_AS` не применяется, процесс использует внешний лимит контейнера/пода, а состояние изоляции явно отображается в диагностике.

   Не включай trusted fallback автоматически в production.

7. После завершения, ошибки, отмены или timeout:

   - заверши всю process group по существующей схеме `SIGTERM` → timeout → `SIGKILL`;
   - освободи GPU в `finally`;
   - удали созданный cgroup;
   - не оставляй процессы и каталоги cgroup.

8. При OOM различай:

   - превышение системной RAM cgroup;
   - исчерпание VRAM, сообщённое Blender/CUDA;
   - обычный `SIGABRT` или другую ошибку Blender.

   Используй counters/events cgroup и лог Blender. Не определяй причину только по `exit code -6`.

9. Мульти-GPU:

   - обнаруживай GPU через NVML при запуске;
   - используй стабильный UUID как внутренний идентификатор, не полагайся только на индекс `0/1/2`;
   - передавай Blender только выделенные scheduler'ом GPU через `CUDA_VISIBLE_DEVICES`;
   - scheduler должен блокировать все GPU задания до его завершения;
   - для анимации должна сохраняться возможность отдельного процесса на GPU;
   - для одного тяжёлого кадра — одного процесса с несколькими выделенными GPU.

   Cgroup ограничивает RAM, но не VRAM. Не изображай VRAM-лимит через cgroup.

10. Не добавляй:

    - глобальную подмену executable Blender;
    - захардкоженные модели поддерживаемых GPU;
    - автоматическое отключение OptiX для RTX A5000;
    - пользовательские shell-команды;
    - `shell=True`;
    - настройку инфраструктурных лимитов через случайный UI-костыль;
    - Docker/Kubernetes orchestration внутри приложения без необходимости.

11. Сохрани текущие публичные API либо выполни полноценную миграцию backend, frontend, тестов и документации. Конфигурация `RENDER_NODE_WORKER_MEMORY_GB` должна означать лимит фактической RAM cgroup либо быть заменена с явной обратной совместимостью и валидацией.

12. Добавь тесты без настоящей GPU:

    - `RLIMIT_AS` больше не устанавливается;
    - создание и настройка fake cgroup v2;
    - обнаружение недоступного/read-only cgroup;
    - strict и trusted режимы;
    - добавление Blender и его потомков в cgroup;
    - распознавание cgroup OOM;
    - cleanup после success/failure/cancel/timeout;
    - освобождение одной и нескольких GPU;
    - корректное формирование `CUDA_VISIBLE_DEVICES`;
    - отсутствие утечек ресурсов при ошибках setup.

    Работу с `/sys/fs/cgroup` абстрагируй ровно настолько, чтобы тестировать через временную файловую структуру. Не добавляй лишнюю инфраструктуру «на будущее».

13. Запусти минимальные релевантные тесты, затем полный доступный backend-набор, lint, formatting и type-check командами, реально объявленными в репозитории.

14. Если окружение не делегирует writable cgroup, не пытайся обходить права и не утверждай, что production-изоляция проверена. Проверь trusted fallback отдельно и опиши необходимые требования к deployment.

15. Обнови:

    - документацию конфигурации и deployment;
    - `IMPLEMENTATION_STATE.md`;
    - описание диагностики OOM.
